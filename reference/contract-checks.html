Match the check to the failure

A check is useful when it observes the kind of thing that could actually go wrong. Every check also leaves a blind spot that belongs in the contract or release decision.

WorkUseful evidenceRemaining blind spot
Pure functionExamples, properties, edge casesThe cases never named
Data pipelineInvariants, reconciliation, historical holdoutsA biased or incomplete reference set
ServiceContract tests, runtime probes, failure injectionProduction conditions the test did not reproduce
InterfaceAccessibility checks, screenshots, interaction tracesTaste, clarity and user context
Code qualityStatic checks, focused independent audit, critical-seam reviewMaintainability outside the review rubric
Risk sets review depth. A low-risk tool may be tested by using it. Inspect security, money, identity, tenancy and irreversible effects closely.

Use this when drafting a contract

  1. Name the concrete failure before choosing a check.
  2. Identify which work surfaces the failure crosses; one task may need several rows.
  3. Choose evidence that can observe that failure independently of the worker's claim.
  4. State the remaining blind spot explicitly.
  5. Increase review depth when blast radius or irreversibility is high.

Applied to the GAiDFLY Prove-It

Data

Historical truth

Assert snapshot and transcript invariants, reconcile stored records, and exercise an existing database rather than only a fresh fixture.

Service

Behavior and failure

Use API contract tests and inject assignment edits, transcript rewrites, cross-tenant access and migration failure.

Critical seam

Independent review

Review authorization and migration code separately because the task touches identity, tenancy and potentially irreversible academic records.

Not in this contract: interface screenshots and judgments about conversation quality. They do not observe the failure this software slice is meant to prevent.
