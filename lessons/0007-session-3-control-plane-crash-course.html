The whole lecture in one path

Request → policy → action → observation → event → reconcile

Before actionValidate the request. Decide allow, ask, or refuse. Record the intent and its stable ID.
During actionRun inside the actual authority and containment boundary. Treat output as untrusted and bounded.
After uncertaintyRead the world. Record what the evidence supports. Never let the model fill the gap with a story.
The failure

A missing answer hides a real effect

A payment, message, deploy, or file write succeeds. The process crashes before recording the result. The log says only that the action was requested.

A blind retry may perform the effect twice. Giving up may leave the world half-changed.

The capability

Evidence-first recovery

Preserve intent before acting. Reuse the same request identity after a crash. Inspect an independent ledger or state surface. Then record ok, failed, or in_doubt.

Your Project 1, not a hypothetical

The session-record action can half-happen

await mkdir(sessionDir);              // the world has changed
// process crashes here
await writeFile("meta.json", ...);   // the evidence record never lands

On resume, the directory exists, so the same request is refused as “already exists.” But no meta.json proves the record was created. The current contract never exercises this crash window.

Stable request ID: sessionId—the identity of the logical creation request, not a fresh attempt ID.

Evidence to read: whether meta.json exists, parses, and contains the fixed seed snapshot.

Honest decision: complete valid file → ok; known empty partial directory → failed plus deliberate recovery; evidence cannot settle it → in_doubt.

Missing control: a reconciliation path or atomic commit strategy. This is a strong candidate for “the moment the run became uncertain” in Project 2.

Active recall · answer before opening

Three checks on your understanding

The tool timed out. Did the action fail?

You do not know. The timeout describes the observation channel. The effect may have landed. Preserve in_doubt until external evidence settles it.

Why is a fresh UUID on every retry not an idempotency key?

It identifies each attempt as a new request. A safe retry must carry the same identity as the original intent so the receiver can recognize it as replay.

What is the control plane in plain English?

Everything between the model asking and the world changing: validation, policy, approval, execution, observation, durable state, and recovery.
